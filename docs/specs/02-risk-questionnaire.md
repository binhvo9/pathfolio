# Feature: Risk Questionnaire → Risk Score + Income Tilt

Status: Implemented & verified live
Service: User & Onboarding

## Problem / goal

The system needs to know two things about a beginner investor before it
can suggest anything: how much volatility can they stomach, and do they
need this money to generate income now or can it just grow untouched.
Two people with identical risk tolerance can need very different
portfolios if one of them needs to live off it.

## Scope

In: the questionnaire itself, additive scoring for both axes, mapping
scores to labeled bands.

Out: turning the scores into an actual asset allocation % — that's the
next spec (`03-allocation-engine.md`). This feature only produces the two
numbers/bands and stores them on RiskProfile.

## Behavior

**Questionnaire** — a handful of multiple-choice questions, each answer
worth points on one or both axes:

- Goal / what is this money for (retirement, house deposit, general growth...)
- Time horizon — years until you expect to need this money
- Risk tolerance — how would you react if your portfolio dropped 20% in a
  month (sell everything / sell some / do nothing / buy more)
- Income need — do you need this portfolio to pay you regular
  income/dividends, or should it just be left to grow

**Scoring** — simple additive, no weighting, same approach for both axes:

1. Each answer has a fixed point value baked into the question definition
2. Risk-axis points sum to a **risk score** → mapped to a band:
   Conservative / Balanced / Growth / Aggressive
3. Income-axis points sum to an **income tilt score** → mapped to a band:
   Growth-focused / Balanced / Income-focused

Both are plain rule-based lookups (score → band via fixed thresholds), no
ML, matching BACKLOG's "rule-based first" for the allocation engine this
feeds into.

**Result:** RiskProfile gets `risk_score`, `risk_band`, `income_tilt_score`,
`income_tilt_band` filled in (previously null after signup, per
`01-auth-user-schema.md`). User is then routed to see their default
allocation, generated by the next feature.

## Data

Adds to `RiskProfile` (from `01-auth-user-schema.md`):
- `goal` (enum), `time_horizon_years` (int)
- `risk_score` (int), `risk_band` (enum: Conservative/Balanced/Growth/Aggressive)
- `income_tilt_score` (int), `income_tilt_band` (enum: GrowthFocused/Balanced/IncomeFocused)
- `questionnaire_completed_at` (timestamp)

Question definitions (text, options, point values) live in code as a
static config, not a DB table — they don't change per-user and don't need
to be queried.

## API / interface

- `POST /api/onboarding/questionnaire` — body: answers to each question;
  computes and persists both scores/bands, returns them
- `GET /api/onboarding/questionnaire` — returns the question definitions
  for the UI to render

## Open questions

None open — score thresholds (exact point cutoffs per band) get decided
during implementation, not architecturally significant enough to block on.
